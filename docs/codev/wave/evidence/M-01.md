## Observations

- Chain-membership differential: expected (independent oracle) `{1, 2, 3}` for chain A and `{4, 5}` for chain B; actual (real PyMOL `copilot_selection` membership after `select copilot_selection, chain A`) `{1, 2, 3}`; zero difference on the true gold case. The wrong-chain negative case's declared expectation (`{4, 5}`, chain B) differs from the real, unchanged PyMOL selection (`{1, 2, 3}`), and the verifier reports that mismatch as a failed assertion.
- Color state: real PyMOL colors `copilot_selection` (chain A, 3 atoms) with the fixture's `red`; `cmd.get_color_index("red")` matches every captured atom color index on the true case, and does not match on the wrong-color negative case (declared expectation `blue`).
- Unintended-change comparison scope: chain B's per-atom `(index, color)` pairs, captured immediately after fixture load and again after the plan executes (and after any injected mutation). The true case shows zero difference; the injected `color blue, chain B` mutation used by `test_unintended_change_is_detected` produces an observed difference, and the assertion correctly fails only that one check while chain-membership and color-state on the target selection still pass.
- Real-PyMOL evaluator-error finding: malformed PyMOL selection syntax (e.g. `"(((not valid"`) does **not** raise a Python exception from `cmd.iterate`/`cmd.count_atoms` in this pinned PyMOL build -- it prints a `Selector-Error` diagnostic to PyMOL's own console and the selection simply matches zero atoms. `cmd.get_color_index` on an unrecognized color name returns `-1` rather than raising. The verifier therefore treats a negative color index as the deterministic, real-PyMOL-surfaced error condition for M-A6's "evaluator error" case; this was confirmed empirically with a disposable debug probe against real PyMOL before being encoded as the negative test.
- Comparison scope and limitations: this receipt's real-PyMOL comparison covers selection membership (by atom index) and per-atom color index only, for the one fixed `select`/`color` fixture. It does not compare coordinates (unchanged by this fixture's operations by construction) or claim whole-session fidelity.
- Conformance disagreements: none observed or filtered. Every assertion result above is reported, including the three deliberately-corrupted negative cases' expected failures.

## Outer-loop finding: real-PyMOL test target's exit code could not be trusted (fixed)

The `concurrency-specialist` outer-loop reviewer found, and I independently confirmed by empirical probe, that `//tests/data:gold_case_verifier` could report Bazel `PASSED` even when a test inside it genuinely failed. Root cause: real headless PyMOL's process-teardown path (triggered by its own internal cleanup during normal Python interpreter shutdown, not specifically by the explicit `cmd.do("quit")` call -- removing that call alone did not fix it) can complete *after* the point a correct process would have already exited, and its own exit path forces process exit code 0, silently overriding whatever real pytest result (0 or 1) was already computed.

**Confirmed empirically, twice:**
- Baseline control: a deliberately failing assertion added to a non-PyMOL target (`//tests/data:gold_case`) correctly reported Bazel `FAILED` -- ruling out a generic Bazel/rules_python exit-code bug.
- Before the fix: the same deliberate failure added to `//tests/data:gold_case_verifier` reported Bazel `PASSED` (`1 failed, 5 passed` in the pytest log, `Executed 1 out of 1 test: 1 test passes` from Bazel) -- reproducing the defect exactly as the specialist described, with and without the explicit `cmd.do("quit")` call present.
- After the fix: the same deliberate failure correctly reported Bazel `FAILED` (`Exit 1`), and removing the probe again correctly reported `PASSED` -- both directions verified, not just the failure case.

**Fix applied** (in `tests/data/test_gold_case_verifier.py`, within M-01's original allowed scope): the module's `if __name__ == "__main__":` entry point now calls `os._exit(pytest.main([__file__]))` instead of `raise SystemExit(pytest.main([__file__]))`. `os._exit` terminates the process immediately with pytest's real result, without running the interpreter-shutdown machinery real PyMOL's cleanup piggybacks on.

A narrow re-verification by the concurrency specialist against the fixed head confirmed the exit-code fix resolves the original finding (empirically reproduced: a deliberate failure now correctly reports Bazel `FAILED`), and surfaced one more real, non-blocking gap: `os._exit` also skips the normal stdio flush, so a genuine failure's traceback and summary could be silently truncated or lost from the captured test log (confirmed empirically: the log ended mid-progress-line with the failure details missing). Fixed by flushing `sys.stdout`/`sys.stderr` explicitly before `os._exit`; re-verified empirically that the full failure report now survives in the log, and that the clean suite still reports `PASSED`.

**Cross-cutting concern, not fixed here:** the already-merged `tests/integration/test_real_pymol_command.py` (H-01, `pmc_client`/`pmc_server` lane) uses the identical `pymol.finish_launching`/`cmd.do("quit")`/`raise SystemExit(pytest.main(...))` pattern and is very likely affected the same way -- meaning that target's own green CI history may not be fully trustworthy either. This file is outside M-01's allowed scope and owned by Hannah's H-01 lane per the wave plan's file ownership; fixing it here would cross that boundary without her involvement. Flagging this explicitly as a needed follow-up (a new tracked issue, or a message to Hannah) rather than silently leaving it or silently fixing someone else's file.
